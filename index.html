Batch size for whole Agent Probe traces

Controlled local retrieval-agent workload · NVIDIA H100 80GB · Llama-3.1-8B-Instruct-AWQ-INT4 · vLLM 0.23.0

With Agent Probe enabled, increasing concurrency from 1 to 32 traces raised total batch completion time only from 0.771 s to 1.358 s, while completing 32 times as many traces in parallel.

What I ran

I used a probe-driver script to run one independent retrieval agent in each batch slot. Every trace was asked: “Why does the Cheshire Cat say that everyone in Wonderland is mad, and what happens to the Cat at the end of its conversation with Alice?”

The system prompt asked the model to state a short search query, then answer from supplied local-book excerpts. Each trace had two model turns and two tool turns. The first model input was 99 tokens on average; after retrieval, the second was 484 tokens. Generation was capped at 128 new tokens per turn, temperature was 0, and the model context limit was 4,096 tokens.

Batch size N means N independent traces running together. Once a trace finishes, it would leave later model batches; in this controlled two-turn workload, all traces follow the same two-turn structure.

Agent Probe here is a Python driver script. For a batch of N, the script creates N independent retrieval-agent requests. On model turn 1, it submits the N prompts to vLLM together. It then runs the local search and passage-reading tools for each trace, appends those tool results to that trace’s conversation, and submits the second-turn prompts together. The reported batch time starts before the first model requests and ends after every trace has completed its second model turn.

Results so far

Across this controlled workload, increasing the number of concurrent traces increases GPU power draw and eventually increases end-to-end completion time. Mean GPU power rose from 283 W at N=1 to 512 W at N=32, while mean batch completion rose from 0.771 s to 1.358 s. The N=2 batch was slightly faster than N=1 in this four-run sample, but the upward trend is clear from N=4 onward.

A recurring feature of each trace is that the higher-power model phase is expected after retrieval. The first model turn sees a 99-token input and produces a short 32-token search request. After the search and passage-reading tools return, the second model turn processes a 484-token input and generates up to 128 tokens. That larger context and longer generation create more GPU work than the initial turn. The local tool calls themselves run on the CPU and take about 7–10 ms per trace, so they do not directly raise GPU power; rather, the passage-reading step makes the following model call more expensive.

How this differs from the fixed-decode baseline

The fixed-decode baseline has no Agent Probe, no tools, no conversation state, and no retrieval. It sends fixed 256-token inputs and generates 512 tokens per request, so it isolates decode contention. Its recorded mean GPU power rose from 281 W at N=1 to 389 W at N=32. This Agent Probe workload instead performs two model turns around local search and passage retrieval; its second model input grows from 99 tokens to 484 tokens after the tool result, and its wall-clock timing includes tool execution. Its mean GPU power rose from 283 W at N=1 to 512 W at N=32.

The model keeps key/value (KV) cache entries for tokens already processed in each active trace. More concurrent traces and a longer second-turn context both increase the amount of active KV cache and attention work. However, this experiment changes N while keeping the retrieval context fixed, so it does not by itself prove how much of the power increase comes from KV cache versus more concurrent decode work. Local tool execution took about 7–10 ms per trace and does not itself use the GPU; the higher GPU power is observed during the model turns.

Although the local tool calls take only about 7–10 ms per trace and do not directly use the GPU, their returned text can still create additional GPU consumption. When retrieved passages are appended to the conversation, the next model turn must prefill those new tokens, write their key/value-cache entries, and attend to the longer context while generating its answer. vLLM can usually reuse cached work for the earlier conversation, so it does not need to recompute the entire trace from scratch; however, the added retrieval context remains a potential source of GPU power and energy use.

Future work will measure this effect more closely and test ways to avoid unnecessary consumption without reducing answer quality: compacting retrieved passages, limiting redundant context, and preserving reusable KV-cache state across tool-return boundaries.

Future work

Next, I will repeat this protocol with different Agent Probe designs and different tools. I will compare search, document retrieval, database lookup, and slower remote-style tool backends; record per-tool latency, model input growth, GPU power, and trace completion time; and test whether each tool type produces a repeatable scaling pattern as batch size increases.

To test the KV-cache hypothesis directly, I will hold batch size and generated-token limits fixed while varying only the amount of retrieved text supplied before the second model turn. This will show whether longer agent context raises average power, peak power, or completion time independently of tool latency and concurrency.

I will also test whether the time between model turns changes the cost of resuming a trace. Holding the retrieved text fixed, I will vary the delay between the tool return and turn 2, while recording KV-cache residency, re-prefill tokens, completion time, GPU power, and energy. If the KV cache remains resident, waiting alone should not require the model to reread the earlier conversation. Under memory pressure or concurrent scheduling, however, a longer delay may allow cached state to be evicted; the resumed turn would then need to rebuild more of its context, increasing latency and potential GPU consumption.
