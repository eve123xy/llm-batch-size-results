Batch size for whole Agent Probe traces

Controlled local retrieval-agent workload · NVIDIA H100 80GB · Llama-3.1-8B-Instruct-AWQ-INT4 · vLLM 0.23.0

With Agent Probe enabled, a full batch of 32 retrieval traces finished in 1.358 seconds on average, versus 0.771 seconds for one trace.

What I ran

I used a probe-driver script to run one independent retrieval agent in each batch slot. Every trace was asked: “Why does the Cheshire Cat say that everyone in Wonderland is mad, and what happens to the Cat at the end of its conversation with Alice?”

The system prompt asked the model to state a short search query, then answer from supplied local-book excerpts. The driver used search_corpus, which ranks Alice in Wonderland paragraphs by word overlap and returns the top three passage IDs, followed by read_passage, which returns those passages verbatim. Each trace had two model turns and two tool turns. The first model input was 99 tokens on average; after retrieval, the second was 484 tokens. Generation was capped at 128 new tokens per turn, temperature was 0, and the model context limit was 4,096 tokens.

Batch size N means N independent traces running together. Once a trace finishes, it would leave later model batches; in this controlled two-turn workload, all traces follow the same two-turn structure.

Agent Probe here is a Python driver script, not a single model request. For a batch of N, the script creates N independent retrieval-agent requests. On model turn 1, it submits the N prompts to vLLM together. It then runs the local search and passage-reading tools for each trace, appends those tool results to that trace’s conversation, and submits the second-turn prompts together. The reported batch time starts before the first model requests and ends after every trace has completed its second model turn.

GPU power

GPU power was sampled every 10 ms across each full batch. Mean power rose with N: 283 W at N=1, 356 W at N=2, 382 W at N=4, 418 W at N=8, 459 W at N=16, and 512 W at N=32. The observed peak increased from 349 W to 549 W. Higher batch sizes therefore increased both completion time and GPU power draw.

How this differs from the fixed-decode baseline

The fixed-decode baseline has no Agent Probe, no tools, no conversation state, and no retrieval. It sends fixed 256-token inputs and generates 512 tokens per request, so it isolates decode contention. Its recorded mean GPU power rose from 281 W at N=1 to 389 W at N=32. This Agent Probe workload instead performs two model turns around local search and passage retrieval; its second model input grows from 99 tokens to 484 tokens after the tool result, and its wall-clock timing includes tool execution. Its mean GPU power rose from 283 W at N=1 to 512 W at N=32.

The model keeps key/value (KV) cache entries for tokens already processed in each active trace. More concurrent traces and a longer second-turn context both increase the amount of active KV cache and attention work. However, this experiment changes N while keeping the retrieval context fixed, so it does not by itself prove how much of the power increase comes from KV cache versus more concurrent decode work. Local tool execution took about 7–10 ms per trace and does not itself use the GPU; the higher GPU power is observed during the model turns.

Future work

Next, I will repeat this protocol with different Agent Probe designs and different tools. I will compare search, document retrieval, database lookup, and slower remote-style tool backends; record per-tool latency, model input growth, GPU power, and trace completion time; and test whether each tool type produces a repeatable scaling pattern as batch size increases.

To test the KV-cache hypothesis directly, I will hold batch size and generated-token limits fixed while varying only the amount of retrieved text supplied before the second model turn. This will show whether longer agent context raises average power, peak power, or completion time independently of tool latency and concurrency.
